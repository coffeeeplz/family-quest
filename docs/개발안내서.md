# 가족 퀘스트: 다음 세션을 위한 개발 안내서

> 기준: v1.15.0 (2026-10-13). 저장소 맨 위의 `CLAUDE.md`가 새 세션에 자동으로 읽히고, 이 문서를 가리킨다. 새 세션은 이 문서부터 읽고 시작한다.
> 앱 설명과 기능 표는 `README.md`, 버전별 변경은 `CHANGELOG.md`(원본은 `src/domain/changelog.ts`)에 있다.

## 1. 소유자와 작업 규칙 (가장 중요)

- 소유자는 부산의 고등학교 수학 교사이고 개발자가 아니다. 답은 **한국어로 간단명료하게** 한다.
- **코딩 용어를 쓸 때는 괄호 안에 일반인도 알아듣게 풀어 쓴다.** 예: PR(합치기 전에 변경 내용을 보여 주는 요청서). 소유자가 이제 괜찮다고 할 때까지 계속한다.
- **코드 수정, 커밋, 병합은 소유자가 `go`(또는 `<작업수행>`)라고 할 때만** 한다. 그 전에는 원인 조사(읽기)와 방안 협의만 한다.
- 작업 흐름
  1. 지정된 작업 브랜치에서 작업한다. 이미 병합된 브랜치라면 최신 `main`에서 다시 시작한다.
  2. 아래 5장의 검증을 모두 돌린다.
  3. 커밋하고 푸시한 뒤 PR을 만든다. PR 하나에는 주제 하나만 담는다. PR을 열면 "미리보기" 작업이 체험 모드 앱을 임시 주소(7일)에 올리고 PR 댓글로 주소를 남긴다. 소유자는 그 주소로 폰에서 먼저 눌러 본다.
  4. 소유자가 **"go 합쳐줘"** 라고 하면 `main`에 병합한다.
  5. GitHub Actions의 "배포" 실행 결과를 확인해서 보고한다. 병합하면 자동으로 배포된다.
- 화면 원칙: 첫 화면에는 핵심만 두고, 나머지는 메뉴, 접는 구역, 안쪽 화면에 넣는다. 한국어 문구는 지금 말투(아이에게 말하듯 쉬운 말)를 따른다.
- 그림: **단순하고 귀여운 16×16 도트 스타일**이다. 32×32로 바꿔 봤지만 소유자가 기존 16×16이 더 귀엽다고 해서 되돌렸다. 꾸미기 배경은 복잡해 보여서 뺐다.
- 버전 번호: 큰 기능은 가운데 숫자(1.14 → 1.15), 작은 고침은 끝 숫자를 올린다. `package.json`, `CHANGELOG.md`, `src/domain/changelog.ts` 세 곳을 함께 고친다(테스트가 셋이 맞는지 검사한다).

## 3. 구조

```
src/domain/    순수 계산·검증(화면·서버 모름). 규칙의 원본
src/backend/   Backend 인터페이스(types.ts)와 두 구현: firebase.ts(실제), demo.ts(체험, localStorage)
src/app/       세션, 가족 데이터 구독(familyData), 화면 틀과 탭(Shell.tsx)
src/features/  화면 단위 폴더(wardrobe, avatar, approvals, quests, shop, notes, notify …)
src/ui/        공통 부품(kit, Sprite, toast) / src/lib/ 날짜·스프라이트·푸시 기기
functions/     알림 서버(Cloud Functions). src/domain 을 그대로 가져다 씀
firestore.rules  보안 규칙(권한과 금액 검증의 최종 방어선)
tests/         vitest(*.test.ts) / tests/rules/*.rules.ts 는 규칙 테스트(에뮬레이터 필요)
tools/         그림 도구, 스티커·꾸미기 추가 도구, e2e(tools/e2e/run.mjs)
```

- 새 기능은 `domain`에 계산을 두고, **firebase.ts와 demo.ts를 똑같이** 구현하고, 규칙과 규칙 테스트를 함께 고친다.
- 화면 경로는 `src/app/Shell.tsx`에 추가한다. 내 캐릭터 화면(이름·캐릭터·색·꾸미기)은 `/wardrobe`이다. 가입할 때만 `features/avatar/ProfileForm.tsx`를 쓴다.
- 날짜는 한국 시각 기준이다. 규칙의 `kstDay()`는 앞뒤 10분의 여유를 둔다.

## 4. 꾸미기 시스템

- **데이터**
  - `src/assets/sprites.json`의 `avatars`: `price`가 0이면 무료 12종이다. `hatY`와 `faceY`는 모자와 얼굴 아이템을 위아래로 옮기는 보정값이다.
  - `src/assets/wardrobe.json`: 아이템 목록 `{id, slot, name, price, rows}`. slot은 `hat`, `face`, `outfit`, `hand` 중 하나다.
- **그리기 순서**(`domain/wardrobe.ts`의 `avatarLayers`): 캐릭터 → 옷 → 얼굴 → 모자 → 소품
- **기준 위치**(토끼·곰): 머리 위 끝 y 4~5, 눈 y 7~8(x 4, 11), 볼 y 9, 몸통 y 11~15(x 3~12), 소품은 오른쪽 x 12~15
- **저장 형식**: 구성원 문서의 `avatar.wear`(입은 것), `wardrobe`(산 것 id), 가격 `families/{fid}/wardrobePrices/{id}`, 장부 id `wardrobe-{uid}-{id}`
- **그림 수정과 추가**
  - 첫 세트는 `python3 tools/avatar_art.py`에 글자 그림으로 들어 있다. 실행하면 JSON과 규칙 목록을 다시 쓴다.
  - 다른 AI가 그린 아이템은 `npx tsx tools/add-wardrobe-item.ts 아이템.json`으로 넣는다.
  - 두 도구 모두 `firestore.rules`의 `wardrobeDefaultPrices`와 `freeAvatarIds`를 자동으로 맞추고, `tests/wardrobe.test.ts`가 둘이 일치하는지 검사한다.
  - 미리보기 그림은 `python3 tools/render_sprites.py src/assets/sprites.json 출력폴더`로 만든다.
- 스티커도 같은 방식이다(`tools/add-sticker-pack.ts`, 규칙의 `stickerPackIds`).

## 5. 검증 (푸시 전에 모두)

```bash
npm ci
npx tsc -b                                  # 타입 검사
npm test                                    # 단위·체험 백엔드 테스트(178개)
npm run test:rules                          # 서버 규칙 테스트(47개). Java 21 필요, Firestore 에뮬레이터를 받아서 돈다
npx tsc -p functions/tsconfig.json --noEmit # 알림 서버 타입 검사
npm run build
```

- 규칙 테스트 중 날짜 관련 테스트는 한국 자정 앞뒤 15분에는 건너뛴다.
- `npx tsc -b`를 돌리면 `tsconfig.tsbuildinfo`가 바뀐다. 커밋하지 말고 `git checkout tsconfig.tsbuildinfo`로 되돌린다.
- **e2e(실제 클릭 점검)**
  ```bash
  npm run build:e2e && npm i --no-save playwright
  APP_DIR=$PWD node tools/e2e/run.mjs   # APP_DIR 꼭 지정(run.mjs 안의 URL 이름 충돌 버그)
  ```
  - 클라우드 환경에서는 `chromium.launch({ executablePath: '/opt/pw-browsers/chromium' })`로 바꾼 복사본을 돌린다.
  - 275개 점검이 통과한 뒤 "위치 권한이 꺼져 있어요" 단계에서 멈추는 것은 **실행 환경 문제**다. 기존 코드도 같은 곳에서 멈춘다.
  - `npm i --no-save playwright`는 `package.json`과 lock 파일을 건드리므로, 끝나면 되돌리고 `npm ci`를 다시 한다.
  - 실행 후 생기는 `e2e-shots/`와 `firestore-debug.log`는 커밋하지 않는다(.gitignore에 있음).
- 체험판은 MemoryRouter라 주소(#/…)로 화면을 바꿀 수 없다. 화면의 버튼을 눌러 이동한다.
- 체험 데이터 저장 키는 `family-quest-demo-v13`이다. 체험 상태의 형식을 바꾸면 v를 올린다.
- CI(`.github/workflows/deploy.yml`, main에 푸시될 때): 검사와 빌드(테스트, 규칙 테스트, 빌드) → 규칙 게시 → 알림 서버 배포 → Pages 배포. "백업 예약 확인"은 따로 돌고 실패해도 배포를 막지 않는다. PR에는 `.github/workflows/preview.yml`(체험 모드 미리보기, Firebase Hosting 임시 주소 `pr-번호`)이 돈다. 규칙 테스트가 실패하면 그 뒤가 모두 멈춘다.

## 6. 데이터 백업

- `deploy.yml`의 "백업 예약 확인" 단계가 main에 올라갈 때마다 Firestore 자동 백업 예약을 확인하고, 없으면 만든다(매일 백업 7일 보관, 매주 일요일 백업 98일 보관). 결과는 실행 기록의 주석(notice)에 남는다.
- 복구는 백업을 **새 데이터베이스**로 되살린 뒤 옮기는 방식이다. 지금 데이터를 덮어쓰지 않는다.
  ```bash
  gcloud firestore backups list --project family-quest-22c44
  gcloud firestore databases restore --project family-quest-22c44 \
    --source-backup=projects/family-quest-22c44/locations/<위치>/backups/<백업id> --destination-database=restored
  ```
  되살린 데이터베이스에서 필요한 문서를 확인하고 옮기는 작업은 소유자와 협의한 뒤에 한다.

## 7. 알려진 문제와 다음 후보

- 소유자 안드로이드 폰의 아이콘 숫자가 남던 문제는 v1.14.1의 알림창 정리 뒤 2026-10-13에 해결됐다고 확인했다. 다시 생기면 알림 설정(`features/notify/NotifyPage.tsx`)에 `AppBadge.tsx`의 정리 함수를 쓰는 "아이콘 숫자 지우기" 버튼을 넣는다.
- **메모·일정·보상 제안을 컬렉션 전체로 구독**(데이터가 쌓이면 읽기가 늘어남): 보류했다. 예전 메모에는 `hiddenAt` 칸이 없을 수 있어서, 조건 조회로 바꾸면 그 메모가 홈에서 사라질 위험이 있다.
- **큰 파일 나누기**: `backend/firebase.ts`, `backend/demo.ts`, `features/approvals/ApprovalsPage.tsx`. 동작은 그대로이고 변경량이 크다.
- **초대코드 1회용 여부**: 지금은 7일 동안 여러 번 쓸 수 있다. 소유자 결정이 필요하다.
- **상점 구매 제한**은 v1.15.0부터 서버 규칙이 지킨다. 제한 있는 보상의 신청 id는 `limit_{uid}_{보상id}_{기간 첫날}_{번호}`이고(`domain/shop.ts`의 `nextOrderSlot`), 번호 1~count만 쓰고 그 위 번호는 count 앞 번호가 거절됐을 때만 쓴다. 규칙은 가진 코인보다 비싼 신청도 막는다. **묶인 코인 합계**(여러 신청의 합)는 규칙으로 셀 수 없어 기기에서 검사하고, 승인할 때 잔액을 다시 확인한다.
- README에 적힌 예정 기능: 주간 요약, 가족 채팅.

## 8. 새 세션 시작 체크리스트

1. 지정 브랜치를 확인하고 최신 `main`에서 시작한다(`git fetch origin main`).
2. `npm ci`를 하고 5장의 검증을 한 번 돌려서 출발점이 정상인지 확인한다.
3. 이 문서, `README.md`, `CHANGELOG.md` 맨 위를 읽는다.
4. 소유자 요청은 먼저 조사하고 협의한 뒤, **`go`를 받고** 작업한다.
5. 끝나면 검증 → PR → "go 합쳐줘" → 병합 → 배포 결과 보고 순서로 마무리한다.
